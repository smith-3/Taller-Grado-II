\section{Fase 2: Modelo de dominio (entidades, reglas, mapeo)}

Esta fase consolida la arquitectura de datos de TecnoTime, estableciendo un modelo de dominio robusto que actúa como el núcleo de la lógica de negocio. Siguiendo los principios de Clean Architecture, este modelo desacopla las reglas académicas de la interfaz de usuario y la persistencia, definiendo las estructuras fundamentales que soportan la generación de horarios, la gestión de preferencias y la interoperabilidad del sistema.

\subsection{Objetivo}
El objetivo principal es formalizar las reglas de negocio del contexto académico en un esquema de datos estricto. Se busca garantizar la integridad referencial entre materias, grupos y docentes, asegurando que todas las operaciones del sistema, desde la visualización hasta la exportación, operen sobre datos consistentes y validados, independientemente de la fuente de origen (PDF o JSON).

\subsection{Implementación del modelo de dominio}
La implementación se articula en tres ejes fundamentales derivados del análisis del código. Primero, se definen entidades ricas (Subject, Group, UserSettings) que encapsulan tanto estado como comportamiento. Segundo, se establecen invariantes de integridad mediante índices únicos y claves foráneas en la capa de persistencia (Room). Finalmente, se implementan estrategias de mapeo bidireccional que transforman estos modelos para su transporte (ShareableScheduleDto) y almacenamiento, manteniendo una clara separación de responsabilidades.

\subsection{Entidades (derivadas del código)}
El modelo de dominio de TecnoTime constituye la representación conceptual del problema de gestión de horarios académicos, traducido a entidades de software que encapsulan tanto datos como comportamiento. Este modelo se deriva directamente del análisis del código fuente implementado, garantizando la trazabilidad entre el diseño conceptual y la implementación real.

Las entidades principales abarcan desde la representación de materias y grupos hasta la gestión de preferencias de usuario y configuraciones del sistema. A continuación se detallan las entidades fundamentales que componen este modelo:

\begin{itemize}
  \item Subject: domain/model/Subject.kt (code, name, isElective, isApproved, isActive).
  \item Group: domain/model/Group.kt (id, subjectCode, groupId, levelId, groupName, type, modality, isActive).
  \item GroupSchedule: domain/model/GroupSchedule.kt (id, groupId, day, startTime, endTime, classroomId, teacherId, isActive).
  \item UserSettings: domain/model/UserSettings.kt (id, userName, use24Hours, showWeekend, isFirstLaunch, showFreeDays, themeDark, enableClassNotifications, classNotificationAdvanceMinutes, enableNoteReminders, noteReminderAdvanceMinutes, enableAi, enableAiInClassNotifications, enableAiInNoteReminders, enableAiEmotionalMonitoring, enableAiMotivationalMessages).
  \item ShareableScheduleDto: domain/model/ShareableScheduleDto.kt (meta, careers, entries).
\end{itemize}

\subsection{Reglas e invariantes}
La integridad del modelo de dominio se sustenta en un conjunto de reglas e invariantes que garantizan la consistencia de los datos a lo largo del ciclo de vida de la aplicación. Estas reglas abarcan desde restricciones de unicidad en identificadores hasta validaciones temporales que aseguran la coherencia de los horarios.

La implementación de estas invariantes se realiza tanto a nivel de base de datos mediante índices y restricciones de integridad referencial, como a nivel de lógica de negocio mediante validaciones en los casos de uso. El cumplimiento estricto de estas reglas previene estados inconsistentes que podrían comprometer la funcionalidad del generador de horarios o la experiencia del usuario. Las reglas establecidas son:

\begin{itemize}
  \item Unicidad de Materia: SubjectEntity define @Index(value = [\textquotedbl code\textquotedbl], unique = true).
  \item Unicidad de Grupo: GroupEntity define @Index(value = [\textquotedbl subject\_code\textquotedbl, \textquotedbl group\_id\textquotedbl], unique = true) y claves foráneas hacia LevelEntity y SubjectEntity con borrado en cascada (ForeignKey.CASCADE).
  \item Integridad de Horario: GroupScheduleEntity define claves foráneas hacia GroupEntity (CASCADE), ClassroomEntity (SET\_NULL) y TeacherEntity (SET\_NULL).
  \item Validaciones de Negocio: GroupSchedule asegura que startTime sea menor a endTime y que los días correspondan a la enumeración WeekDay.
\end{itemize}

\subsection{Mapeos del ingreso al dominio y al almacenamiento}
La arquitectura de TecnoTime implementa una clara separación entre las capas de ingreso de datos, dominio y persistencia, requiriendo transformaciones explícitas entre las representaciones de cada capa. Los mapeos bidireccionales permiten convertir datos desde formatos externos como PDF y JSON hacia el modelo de dominio, y posteriormente hacia entidades de base de datos para su almacenamiento persistente.

Esta estrategia de mapeo explícito facilita la evolución independiente de cada capa, permite la validación de datos en cada transformación y simplifica las pruebas unitarias al aislar las responsabilidades de cada componente. Los principales componentes de mapeo implementados son:

\begin{itemize}
  \item Ingreso de Datos: GenerateShareableScheduleJsonUseCase orquesta la obtención de información académica (GetAcademicInfoUseCase) y horarios semanales (GetWeeklyEnrolledScheduleUseCase), filtrando por materias seleccionadas.
  \item Transferencia de Datos: ShareableScheduleDto estructura la información para exportación/importación, encapsulando metadatos, carreras y entradas de horario.
  \item Persistencia: Los repositorios transforman entidades de dominio a entidades de Room (e.g., Subject a SubjectEntity) asegurando que la estructura relacional se mantenga en la base de datos SQLite.
\end{itemize}

\subsection{Implementación técnica del dominio}
La implementación del modelo de dominio se materializa en un conjunto de clases Kotlin que reflejan fielmente el diseño conceptual presentado. Estas clases, organizadas en el paquete domain model, siguen los principios de inmutabilidad y encapsulamiento propios de la programación funcional, utilizando data classes para garantizar la integridad de los datos en memoria.

Componentes principales del modelo:
\begin{itemize}
  \item Subject: Representa la entidad fundamental de la materia. Se define por un código único que actúa como identificador, un nombre descriptivo y un conjunto de banderas de estado booleanas. La propiedad isElective distingue las materias optativas, isApproved permite marcar las materias ya cursadas y aprobadas por el alumno, y isActive gestiona la vigencia de la materia en el plan de estudios actual.
  \item Group: Modela la unidad académica de cursada vinculada a una materia específica mediante el subjectCode. Cada grupo posee un identificador único y atributos detallados como el groupId visible para el usuario (ej. ``1'', ``A''), el levelId que lo asocia a un nivel o semestre específico, y el tipo de grupo que diferencia entre clases teóricas y prácticas. Además, incluye la modalidad de dictado y un estado de actividad.
  \item GroupSchedule: Define los bloques temporales asociados a un grupo. Esta entidad valida la coherencia temporal asegurando que la hora de inicio sea anterior a la de fin y utiliza el enumerado WeekDay para garantizar días válidos. Vincula cada horario con un aula (classroomId) y un docente (teacherId), permitiendo una representación detallada de la agenda semanal.
  \item UserSettings: Centraliza las preferencias de personalización del usuario en un registro único. Abarca configuraciones de visualización como el tema oscuro (themeDark) y el formato de hora, así como opciones avanzadas de inteligencia artificial. Estas incluyen banderas para habilitar el monitoreo emocional, mensajes motivacionales y el uso de IA en notificaciones, permitiendo una experiencia adaptativa.
  \item ShareableScheduleDto: Estructura de transferencia de datos diseñada para la exportación e importación de horarios. Encapsula una lista de carreras, metadatos de versión y una colección de entradas de horario (entries). Esta clase actúa como un contrato de datos que facilita la interoperabilidad entre diferentes instancias de la aplicación, asegurando que toda la información necesaria para reconstruir un horario esté contenida en un único objeto transferible.
\end{itemize}

En la capa de persistencia, las entidades definidas en data local entity actúan como espejo del dominio pero enriquecidas con anotaciones de la librería Room. La clase SubjectEntity mapea la tabla subjects y establece un índice único sobre el campo code para asegurar la identidad de cada materia. De manera similar, GroupEntity representa la tabla groups y define un índice compuesto sobre el código de materia y el identificador de grupo para evitar duplicados.

Además, la entidad GroupEntity implementa restricciones de integridad referencial mediante claves foráneas hacia las tablas de niveles y materias, configuradas con reglas de borrado en cascada para mantener la consistencia de la base de datos.

La lógica de negocio se orquesta a través de casos de uso ubicados en el paquete domain usecase. Un componente destacado es GenerateShareableScheduleJsonUseCase, el cual encapsula la complejidad de la exportación de horarios. Este caso de uso coordina la obtención de información académica y horarios semanales, filtra los datos según las materias seleccionadas por el usuario y transforma la información resultante en una estructura de transferencia optimizada, asegurando que los datos exportados sean completos y coherentes para su uso externo.

\subsection{Resultados y verificación}
El modelo de dominio se valida mediante pruebas de integración que confirman la integridad referencial y la unicidad de claves compuestas. Los mapeos bidireccionales entre las capas de datos, dominio y presentación se verifican exhaustivamente, asegurando la consistencia de la información en todo el flujo de la aplicación.
