\section{Fase 1: Ingestión y normalización (de PDF a BD)}

Esta fase establece el pipeline fundamental para la adquisición y normalización de datos académicos provenientes de los documentos PDF oficiales de la UMSS. Dada la naturaleza no estructurada y la variabilidad del formato fuente, esta etapa es crítica para garantizar la calidad y consistencia de la información que alimentará al generador de horarios.

Para ello, se implementa un flujo ETL (Extracción, Transformación y Carga) autónomo que se ejecuta en su totalidad en el dispositivo del usuario (Edge Computing). Esta estrategia descentralizada no solo optimiza el uso de recursos limitados del servidor, sino que también permite la operatividad del sistema incluso en entornos con conectividad intermitente o nula.

El alcance de esta fase se limita al consumo no invasivo de información pública ya publicada por la facultad. No se establece una integración transaccional con sistemas institucionales ni se modifican sus procesos internos. La aplicación consulta la fuente disponible, descarga el documento de horarios cuando corresponde y transforma su contenido a un modelo local para uso del estudiante.

\subsection{Objetivo}
El objetivo es transformar la información semi-estructurada de los horarios oficiales a un modelo de datos relacional estrictamente tipado y normalizado. Durante este proceso, se valida de forma rigurosa la integridad referencial de entidades clave como materias, grupos y docentes, asegurando que no existan inconsistencias en la base de datos local.

Asimismo, se minimiza el impacto en la infraestructura tecnológica de la universidad mediante estrategias de caché inteligente y sincronización diferencial, evitando descargas innecesarias. De esta manera, se logra un equilibrio óptimo entre la frescura de los datos y la eficiencia operativa, reduciendo de forma considerable el consumo de ancho de banda del estudiante.

Al iniciar el generador de horarios, el sistema evalúa la conectividad y la vigencia de los datos locales para decidir la estrategia de obtención más eficiente. Esta coordinación lógica se materializa a través de los siguientes componentes especializados que aseguran la integridad del flujo:

\begin{itemize}
  \item Orquestación de UI: El componente GenerateScheduleViewModel actúa como el controlador central de la experiencia, gestionando el estado de la interfaz de usuario. Su función es bloquear las acciones de generación únicamente durante los momentos críticos de sincronización.
  \item Diagnóstico de Red: La clase NetworkConnectivityChecker realiza una verificación exhaustiva que valida la capacidad real de transmisión de datos, discriminando de forma eficaz entre estados online y offline para evitar errores de conexión.
  \item Sincronización y Resiliencia: El caso de uso AutoSyncUseCase es el núcleo lógico que determina si es necesaria una actualización. Incorpora patrones como Circuit Breaker, que previene fallos en cascada, y Exponential Backoff, que gestiona reintentos progresivos.
  \item Preferencias: El componente SyncPreferences actúa como un regulador de tráfico, controlando la frecuencia de las verificaciones automáticas mediante una ventana de tiempo configurable para optimizar el consumo de batería y datos.
\end{itemize}

La orquestación coordinada de estos componentes especializados garantiza que el proceso de adquisición, análisis y normalización de datos se realice bajo condiciones estrictamente controladas de red y almacenamiento local. Este flujo estructurado no solo previene la corrupción de la información durante la descarga, sino que también optimiza el consumo de recursos del dispositivo, asegurando que la transición desde el formato no estructurado del PDF hacia el modelo relacional de la base de datos sea íntegra, trazable y resiliente ante posibles fallos de conectividad.

\subsubsection{4.2.2 Ingesta, análisis y persistencia con frescura}
Ante una actualización, el flujo descarga el PDF oficial y delega el procesamiento al componente PdfParser (ubicado en data.remote.pdf). Este componente implementa una estrategia de análisis sintáctico basada en expresiones regulares (Regex) para estructurar la información no estructurada del documento, manejando la complejidad inherente a los reportes generados por el sistema universitario.

El procesamiento de los documentos PDF para la extracción de datos académicos requiere una metodología estructurada que garantice la precisión de la información. En este sentido, el proceso de análisis se descompone en las dos etapas fundamentales descritas a continuación:
\begin{enumerate}
    \item Fusión de líneas (Merge): Para resolver la fragmentación de nombres de docentes que, debido a su longitud, se distribuyen en múltiples líneas visuales en el PDF, el algoritmo mergeTeacherLines implementa una máquina de estados simple.

    Esta lógica acumula en un buffer temporal cualquier línea de texto que no coincida con los patrones estructurales (como cabeceras o líneas de horario completas) ni con patrones de ruido (e.g., ``Procesado CPD'', ``Página X de Y''). Este contenido acumulado se antepone a la siguiente línea de horario válida detectada, reconstruyendo así la fila lógica completa antes de aplicar la extracción por expresiones regulares.
    
    \item Extracción de patrones: Se implementan dos expresiones regulares principales para la identificación de entidades:
    
    \begin{itemize}
        \item Cabecera de materia (courseLine): Diseñada para capturar la línea que introduce una nueva asignatura:
        \begin{itemize}
            \item Patrón: \textasciicircum([A-Z])\textbackslash s+(\textbackslash d\{7\})\textbackslash s+(.+)\$
            \item Estructura: Captura el Nivel (Grupo 1), el Código de 7 dígitos (Grupo 2) y el Nombre de la materia (Grupo 3).
        \end{itemize}
        
        \item Línea de horario (scheduleLine): Utiliza el modo VERBOSE para procesar una estructura compleja con grupos nombrados:
        \begin{itemize}
            \item group: Identifica el código del grupo (e.g., 1, A, 1A).
            \item type: Captura opcionalmente el tipo de clase entre corchetes (e.g., [P]).
            \item teacher: Extrae el nombre del docente. Dado que este campo tiene longitud variable, se utiliza un lookahead positivo (?=\textbackslash s+[A-Z]\{2\}\textbackslash s+\textbackslash d) para detener la captura exactamente antes de que comience el patrón de día y hora.
            \item day: Captura la abreviación del día de dos letras (e.g., LU, MA).
            \item hour: Captura el intervalo de tiempo, permitiendo espacios flexibles.
            \item classroom: Captura el identificador del aula al final de la línea.
        \end{itemize}
    \end{itemize}
\end{enumerate}

Los datos extraídos se mapean a objetos intermedios SubjectInfo, donde se aplica lógica de negocio adicional para manejar casos especiales:
\begin{itemize}
    \item Herencia de docentes: Si una línea de horario no especifica docente (campo vacío o ``[``), se hereda el último docente válido detectado en el bloque, asumiendo que pertenece al mismo grupo.
    \item Docentes por designar: Se normalizan valores vacíos a ``POR DESIGNAR DOCENTE''.
    \item Separación de Laboratorios: El caso de uso ImportCareerSchedulesUseCase detecta grupos híbridos (e.g., ``1A'' con tipo ``[P]'') mediante la función shouldSplitAsLab. Estos se separan en una ``materia virtual'' con sufijo \_LAB (e.g., ``FISICA GENERAL\_LAB'') para diferenciar académicamente la carga teórica de la práctica en la persistencia.
\end{itemize}

La persistencia de la información en la base de datos local Room se rige por políticas de resolución de conflictos mediante el patrón Upsert (Update or Insert), asegurando la integridad referencial de los datos académicos. Este mecanismo garantiza que, ante la detección de un horario preexistente para una misma terna de grupo, día y hora, el sistema realice una actualización selectiva.

Dicha actualización se aplica únicamente sobre los atributos volátiles, como el aula o el docente asignado. Al preservar la clave primaria y la identidad del registro original, se evita la redundancia de datos y se mantiene la consistencia histórica del perfil del estudiante, incluso tras múltiples ciclos de sincronización diferencial.

Para proteger la estabilidad de la fuente externa y garantizar la frescura de la información, el sistema incorpora patrones de resiliencia y gestión de datos que aseguran la disponibilidad del servicio bajo diversas condiciones operativas:

\begin{itemize}
  \item Descubrimiento y descarga: ScheduleScraper localiza la URL del recurso y PdfDownloader gestiona la descarga segura al almacenamiento local del dispositivo.
  \item Gestión de frescura: Tras una actualización exitosa, se registra el instante de verificación en SyncPreferences, evitando consultas redundantes dentro de una ventana de tiempo configurable.
  \item Mecanismos de robustez: Se implementa ExponentialBackoff para gestionar reintentos ante fallos transitorios y CircuitBreaker para prevenir la saturación del servidor interrumpiendo solicitudes tras errores continuos.
  \item Estrategia de respaldo: En ausencia de conectividad, el sistema permite la importación manual desde un archivo PDF local, asegurando la operatividad total en modo offline.
\end{itemize}

\subsection{Resultados y verificación}
Esta fase establece los cimientos para la adquisición de datos. Se verifica la consistencia de la base de datos por carrera, nivel, materia y grupo, asegurando que el lastSyncTime se actualice correctamente tras una ingesta exitosa.

Las pruebas confirman la robustez del proceso ante fallos de red mediante los mecanismos de backoff y circuit breaker. Estas medidas garantizan que la aplicación sea resiliente en entornos de conectividad inestable.

La integridad semántica de la información se garantiza mediante el uso de enumeraciones de dominio que normalizan los datos extraídos del documento fuente. Estas estructuras permiten transformar representaciones textuales heterogéneas en tipos de datos estrictamente tipados.

Asimismo, aseguran que atributos como los días de la semana y las modalidades de clase sigan un esquema consistente. La validación rigurosa del proceso de ingestión se sustenta en las evidencias técnicas y las métricas de desempeño que se detallan seguidamente:

\begin{enumerate}
  \item Evidencias (código): La implementación integra AutoSyncUseCase y SyncPreferences para la sincronización. Se emplean ScheduleScraper y PdfParser para la ingesta, asegurando resiliencia mediante ExponentialBackoff y CircuitBreaker.

  \item KPIs verificados:
  \begin{itemize}
    \item Cache hit-rate semanal $\geq 80\%$.
    \item Reintentos acotados dentro de los parámetros del backoff.
    \item Tiempo de ingesta por PDF dentro del objetivo operacional.
  \end{itemize}
\end{enumerate}
