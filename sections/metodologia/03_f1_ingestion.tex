\section{F1: Ingestión y normalización (de PDF a BD)}

Esta fase establece el pipeline fundamental para la adquisición y normalización de datos académicos provenientes de los documentos PDF oficiales de la UMSS. Dada la naturaleza no estructurada y la variabilidad del formato fuente, esta etapa es crítica para garantizar la calidad y consistencia de la información que alimentará al generador de horarios.

Para ello, se implementó un flujo ETL (Extracción, Transformación y Carga) autónomo que se ejecuta íntegramente en el dispositivo del usuario (Edge Computing). Esta estrategia descentralizada no solo optimiza el uso de recursos limitados del servidor, sino que también permite la operatividad del sistema incluso en entornos con conectividad intermitente o nula.

\subsection{Objetivo}
El objetivo principal es transformar la información semi-estructurada de los horarios oficiales a un modelo de datos relacional estrictamente tipado y normalizado. Durante este proceso, se valida rigurosamente la integridad referencial de entidades clave como materias, grupos y docentes, asegurando que no existan inconsistencias en la base de datos local.

Asimismo, se minimiza el impacto en la infraestructura tecnológica de la universidad mediante estrategias de caché inteligente y sincronización diferencial, evitando descargas innecesarias. De esta manera, se logra un equilibrio óptimo entre la frescura de los datos y la eficiencia operativa, reduciendo significativamente el consumo de ancho de banda del estudiante.

Al iniciar el generador de horarios, el sistema evalúa inmediatamente la conectividad y la vigencia de los datos locales para decidir la estrategia de obtención de datos más eficiente. Si el contenido almacenado es reciente y válido, se utiliza la caché local para ofrecer una respuesta instantánea; de lo contrario, se inicia una sincronización en segundo plano. Esta lógica de decisión coordina los siguientes componentes especializados:

\begin{itemize}
  \item Orquestación de UI: El componente GenerateScheduleViewModel actúa como el controlador central de la experiencia, gestionando el estado de la interfaz de usuario. Su función es bloquear las acciones de generación únicamente durante los momentos críticos de sincronización para evitar inconsistencias en los datos, manteniendo al usuario informado del progreso sin interrumpir su flujo de trabajo.
  \item Diagnóstico de Red: La clase NetworkConnectivityChecker realiza una verificación exhaustiva que va más allá de detectar una conexión activa. Valida la capacidad real de transmisión de datos hacia internet antes de intentar cualquier operación remota, discriminando eficazmente entre estados online y offline para evitar errores de conexión frustrantes.
  \item Sincronización y Resiliencia: El caso de uso AutoSyncUseCase es el núcleo lógico que determina si es necesaria una actualización, comparando las fechas de modificación de los archivos remotos con los locales. Para garantizar la robustez, incorpora patrones de resiliencia como Circuit Breaker, que previene fallos en cascada interrumpiendo las peticiones si el servidor universitario no responde, y Exponential Backoff, que gestiona reintentos progresivos ante errores transitorios de red.
  \item Preferencias: El componente SyncPreferences actúa como un regulador de tráfico, controlando la frecuencia de las verificaciones automáticas mediante una ventana de tiempo configurable (por defecto 6 horas). Esto evita consultas redundantes al servidor en sesiones de uso frecuente, optimizando tanto el consumo de batería como el uso de datos móviles del estudiante.
\end{itemize}

\subsubsection{4.2.2 Ingesta, análisis y persistencia con frescura}
Ante una actualización, el flujo descarga el PDF oficial y delega el procesamiento al componente PdfParser (ubicado en data.remote.pdf). Este componente implementa una estrategia de análisis sintáctico basada en expresiones regulares (Regex) para estructurar la información no estructurada del documento, manejando la complejidad inherente a los reportes generados por el sistema universitario.

El proceso de análisis se divide en dos etapas principales:
\begin{enumerate}
    \item Fusión de líneas (Merge): Para resolver la fragmentación de nombres de docentes que, debido a su longitud, se distribuyen en múltiples líneas visuales en el PDF, el algoritmo mergeTeacherLines implementa una máquina de estados simple. Acumula secuencialmente en un buffer temporal cualquier línea de texto que no coincida con los patrones estructurales (como cabeceras o líneas de horario completas) ni con patrones de ruido (e.g., ``Procesado CPD'', ``Página X de Y''). Este contenido acumulado se antepone a la siguiente línea de horario válida detectada, reconstruyendo así la fila lógica completa antes de aplicar la extracción por expresiones regulares.
    
    \item Extracción de patrones: Se implementaron dos expresiones regulares principales para la identificación de entidades:
    
    \begin{itemize}
        \item Cabecera de materia (courseLine): Diseñada para capturar la línea que introduce una nueva asignatura.
        \begin{itemize}
            \item Patrón: \textasciicircum([A-Z])\textbackslash s+(\textbackslash d\{7\})\textbackslash s+(.+)\$
            \item Estructura: Captura el Nivel (Grupo 1), el Código de 7 dígitos (Grupo 2) y el Nombre de la materia (Grupo 3).
        \end{itemize}
        
        \item Línea de horario (scheduleLine): Utiliza el modo VERBOSE para procesar una estructura compleja con grupos nombrados:
        \begin{itemize}
            \item group: Identifica el código del grupo (e.g., 1, A, 1A).
            \item type: Captura opcionalmente el tipo de clase entre corchetes (e.g., [P]).
            \item teacher: Extrae el nombre del docente. Dado que este campo tiene longitud variable, se utiliza un lookahead positivo (?=\textbackslash s+[A-Z]\{2\}\textbackslash s+\textbackslash d) para detener la captura exactamente antes de que comience el patrón de día y hora.
            \item day: Captura la abreviación del día de dos letras (e.g., LU, MA).
            \item hour: Captura el intervalo de tiempo, permitiendo espacios flexibles.
            \item classroom: Captura el identificador del aula al final de la línea.
        \end{itemize}
    \end{itemize}
\end{enumerate}

Los datos extraídos se mapean a objetos intermedios SubjectInfo, donde se aplica lógica de negocio adicional para manejar casos especiales:
\begin{itemize}
    \item Herencia de docentes: Si una línea de horario no especifica docente (campo vacío o ``[``), se hereda el último docente válido detectado en el bloque, asumiendo que pertenece al mismo grupo.
    \item Docentes por designar: Se normalizan valores vacíos a ``POR DESIGNAR DOCENTE''.
    \item Separación de Laboratorios: El caso de uso ImportCareerSchedulesUseCase detecta grupos híbridos (e.g., ``1A'' con tipo ``[P]'') mediante la función shouldSplitAsLab. Estos se separan en una ``materia virtual'' con sufijo \_LAB (e.g., ``FISICA GENERAL\_LAB'') para diferenciar académicamente la carga teórica de la práctica en la persistencia.
\end{itemize}

La persistencia en la base de datos Room aplica políticas de conflicto (Upsert) para mantener la integridad referencial. Si se detecta un horario existente para un mismo grupo, día y hora, se actualizan únicamente los campos de aula y docente si han cambiado, preservando la identidad del registro.

Para proteger la estabilidad de la fuente externa y la experiencia del usuario, se aplican patrones de resiliencia:
\begin{itemize}
  \item Descubrimiento/descarga: ScheduleScraper localiza la URL del recurso y PdfDownloader gestiona la descarga segura al almacenamiento local.
  \item Frescura: Tras una actualización exitosa, se registra el lastSyncTime por carrera y se guarda el instante de la verificación en SyncPreferences, evitando consultas redundantes dentro de una ventana de tiempo configurable (e.g., 6 horas).
  \item Robustez: ExponentialBackoff gestiona los reintentos ante fallos transitorios de red (e.g., timeouts), mientras que CircuitBreaker previene la saturación del servidor interrumpiendo temporalmente las solicitudes tras detectar una tasa de error elevada.
  \item Respaldo: En ausencia de conectividad, el sistema permite la importación manual desde un archivo PDF local y opera totalmente en modo offline utilizando los datos en caché.
\end{itemize}

\subsection{Resultados y verificación}
Esta fase estableció los cimientos para la adquisición de datos. Se verificó la consistencia de la base de datos por carrera, nivel, materia y grupo, asegurando que el lastSyncTime se actualice correctamente tras una ingesta exitosa. Las pruebas confirmaron la robustez del proceso ante fallos de red mediante los mecanismos de backoff y circuit breaker.

\begin{enumerate}
  \item Evidencias (código): La implementación integra AutoSyncUseCase y SyncPreferences para la sincronización. Se emplean ScheduleScraper y PdfParser para la ingesta, asegurando resiliencia mediante ExponentialBackoff y CircuitBreaker.

  \item KPIs verificados:
  \begin{itemize}
    \item Cache hit-rate semanal $\geq 80\%$.
    \item Reintentos acotados dentro de los parámetros del backoff.
    \item Tiempo de ingesta por PDF dentro del objetivo operacional.
  \end{itemize}
\end{enumerate}
