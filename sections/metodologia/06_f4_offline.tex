\section{Fase 4: Prioridad sin conexión (frescura, políticas, fallback)}

Esta fase establece la arquitectura offline-first de la aplicación, priorizando la disponibilidad y consistencia de datos locales mediante políticas de frescura, sincronización controlada y mecanismos de resiliencia.

\subsection{Objetivo}
Asegurar disponibilidad sin red priorizando la caché local, controlando frescura y habilitando recuperación manual por PDF.

\subsection{Implementación de Persistencia Local (Room)}
La arquitectura offline-first se sustenta en el uso de la librería Android Jetpack Room, que proporciona una capa de abstracción sobre SQLite para permitir un acceso robusto a la base de datos.

\subsubsection{Entidades de Datos}
El modelo de datos local se define mediante entidades anotadas. La clase SubjectEntity representa la tabla subjects, que almacena la información de las materias. Sus campos principales incluyen:
\begin{itemize}
    \item code: Identificador único de la materia (clave primaria).
    \item name: Nombre descriptivo de la materia.
    \item is\_approved: Estado que indica si la materia ha sido aprobada por el estudiante.
    \item is\_elective: Indicador de si la materia es electiva.
    \item is\_active: Estado lógico para el borrado suave o deshabilitación.
\end{itemize}

\subsubsection{Objetos de Acceso a Datos (DAOs)}
El acceso a la base de datos se realiza a través de interfaces DAO (Data Access Object). SubjectDao define las operaciones CRUD y consultas complejas. Un aspecto clave es el uso de tipos de retorno reactivos como Flow, lo que permite a la interfaz de usuario observar cambios en los datos y actualizarse automáticamente:
\begin{itemize}
    \item upsert(subject): Inserta o actualiza una materia utilizando la estrategia de conflicto REPLACE.
    \item getSubjectsForCareerAndLevelFlow(careerCode, levelId): Retorna un flujo reactivo de materias filtradas por carrera y nivel, realizando un JOIN con las tablas groups y career\_subject\_groups.
\end{itemize}

\subsection{Repositorio y Fuente de Verdad}
Se implementa el patrón Repository para mediar entre las fuentes de datos y la capa de dominio. SubjectRepositoryImpl actúa como la ``Single Source of Truth'' (Fuente Única de Verdad):
\begin{itemize}
    \item Los métodos del repositorio, como getSubjectsForCareerFlow, exponen datos directamente desde la base de datos local (DAO).
    \item Las operaciones de red no retornan datos directamente a la UI, sino que actualizan la base de datos local, lo que a su vez dispara la emisión de nuevos datos a través de los flujos observados.
\end{itemize}

\subsection{Sincronización y Frescura de Datos}
El mantenimiento de la consistencia y frescura de la información en un entorno desconectado requiere de una lógica de sincronización robusta. En este sentido, la implementación se fundamenta en los pilares estratégicos que se describen a continuación:

\begin{enumerate}
    \item Detección de Cambios
    
    Antes de iniciar una descarga completa, el sistema verifica si existen actualizaciones comparando la fecha de modificación remota con la fecha de la última sincronización local almacenada en la carrera. Si los datos temporales coinciden, se evita el consumo innecesario de red y se mantiene la versión actual de la caché.

    \item Manejo de Errores y Resiliencia
    
    Para garantizar la robustez ante fallos de red o indisponibilidad del servidor, se implementan mecanismos de protección que aseguran la continuidad operativa:

    \begin{itemize}
        \item Interruptor de circuito: El componente de protección envuelve las llamadas al extractor de datos. Si se detectan fallos consecutivos, el circuito se abre temporalmente para impedir nuevas solicitudes y evitar la saturación del servidor o de la red móvil.
        \item Espera exponencial: En caso de errores recuperables como tiempos de espera agotados, se programa un reintento automático utilizando una estrategia de espera exponencial. El tiempo de demora se duplica tras cada intento fallido, reduciendo la carga sobre la infraestructura.
    \end{itemize}
\end{enumerate}

\subsection{Fallback Manual}
Como medida de último recurso, cuando no hay conectividad y la base de datos está vacía o desactualizada, se habilita la funcionalidad de ingesta manual. El caso de uso de sincronización desde documento local permite al usuario seleccionar un archivo PDF oficial descargado previamente. El sistema procesa este archivo íntegramente en el dispositivo para poblar las tablas locales, asegurando la operatividad total de la aplicación en entornos aislados.

\subsection{Notificaciones y Asistencia por Inteligencia Artificial}
La implementación utiliza herramientas de programación diferida para asegurar la ejecución de recordatorios incluso tras reinicios del sistema o si la aplicación no está en primer plano. Los componentes de gestión orquestan la lógica de disparo calculando los tiempos de antelación configurados por el estudiante para cada actividad académica. Se emplea un canal estandarizado que garantiza la compatibilidad con versiones modernas del sistema operativo sin requerir conectividad permanente.

La integración de inteligencia artificial opera bajo una lógica de respaldo que prioriza la puntualidad de los avisos. El gestor verifica las preferencias del usuario y solicita una reserva de recursos computacionales antes de invocar la generación del mensaje para evitar la saturación del hardware. En caso de indisponibilidad del modelo local o fallos en la inferencia, el sistema degrada de forma automática a una notificación estándar, garantizando la entrega de la alerta académica.

Para los mensajes motivacionales, el asistente valida el contexto temporal y la carga académica actual, evitando comunicaciones intrusivas durante periodos de descanso activo. El proceso asegura que el tono del mensaje sea oportuno y coherente con la situación del estudiante. Este mecanismo permite al asistente aprender de la respuesta del usuario, ajustando la entrega de futuros mensajes de forma dinámica para optimizar el impacto en el rendimiento.

El sistema registra cada intento mediante identificadores de franja horaria que asocian las acciones de apertura o descarte con el origen del mensaje. Estos identificadores alimentan las métricas estadísticas locales sin comprometer la fluidez de la aplicación ni requerir el envío de información sensible hacia servidores externos. Este flujo de datos permite evaluar la efectividad del agente inteligente preservando el control total del usuario sobre su información.

Este registro se realiza sin exponer datos personales ni acoplar el contenido generado a la identidad del estudiante, garantizando la privacidad por diseño. El agente inteligente opera de forma independiente al núcleo funcional, permitiendo que la base de datos mantenga su integridad estructural ante posibles cambios futuros en los modelos de lenguaje. Esta separación asegura la robustez y escalabilidad de las capacidades cognitivas del sistema.

\subsection{Resultados y verificación}
La arquitectura offline-first demuestra su eficacia al permitir la operación continua sin conectividad, sirviendo datos desde la caché local de Room. Las pruebas de estrés confirman que los mecanismos de backoff exponencial y circuit breaker protegen adecuadamente la fuente de datos ante fallos repetidos. El fallback manual mediante PDF local funciona correctamente como medida de último recurso.

\subsection{Evidencias (código)}
La arquitectura offline-first de TecnoTime se sustenta en un conjunto de componentes que gestionan la sincronización diferida, el almacenamiento local prioritario y las políticas de frescura de datos. La implementación utiliza WorkManager para programar tareas de sincronización en segundo plano que respetan las restricciones de red y batería del dispositivo, mientras que Room proporciona la capa de persistencia local con soporte para observación reactiva de cambios.

Los repositorios implementan el patrón Single Source of Truth, exponiendo siempre los datos locales a la UI y actualizándolos transparentemente cuando la sincronización completa exitosamente. Esta arquitectura garantiza una experiencia de usuario fluida independientemente de la conectividad de red. Los componentes del sistema que materializan estas capacidades de resiliencia y persistencia se detallan seguidamente:

\begin{itemize}
  \item Control de sincronización: ViewModel de generación y banderas de estado.
  \item Detección de red: Verificador de conectividad y preferencias de sincronización.
  \item Fallback manual: Caso de uso de sincronización desde documento PDF local.
  \item Gestión de alertas: Trabajadores de notificaciones y gestor de recursos de IA.
\end{itemize}
