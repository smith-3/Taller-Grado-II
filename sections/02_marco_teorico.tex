\chapter{MARCO TEÓRICO}
\label{chap:marco-teorico}

Este capítulo establece los fundamentos teóricos y tecnológicos relacionados con la ingeniería de software móvil moderna, la arquitectura de software escalable, los algoritmos de optimización y la inteligencia artificial en el borde (Edge AI). Además, se abordan las técnicas de adquisición y procesamiento de datos desde fuentes heterogéneas, como páginas web y documentos estructurados.

El marco conceptual presentado proporciona la base necesaria para comprender las decisiones de diseño e implementación descritas en capítulos posteriores, fundamentando cada elección tecnológica en principios establecidos por la comunidad académica y la industria del desarrollo de software.

\section{Metodologías de Desarrollo de Software}
\label{sec:metodologias}

Las metodologías de desarrollo de software establecen el marco de trabajo para organizar, planificar y ejecutar proyectos de software. Se distinguen dos enfoques principales: las metodologías tradicionales (como Waterfall) y las metodologías ágiles.

\subsection{Metodologías Ágiles}
Las metodologías ágiles surgieron como respuesta a las limitaciones de los enfoques tradicionales en entornos de alta incertidumbre. El Manifiesto Ágil (2001) establece cuatro valores fundamentales: priorizar individuos sobre procesos, software funcional sobre documentación, colaboración con el cliente sobre contratos, y respuesta al cambio sobre seguir un plan \cite{agile_manifesto}.

\subsection{Kanban}
Kanban es un método de gestión visual del trabajo que limita el trabajo en progreso (WIP) para maximizar el flujo y la eficiencia. Originado en el sistema de producción de Toyota, se adaptó al desarrollo de software para visualizar el flujo de trabajo, identificar cuellos de botella y promover la mejora continua \cite{kanban_anderson}.

\section{Ingeniería de Software para Dispositivos Móviles}
\label{sec:ingenieria-movil}

El desarrollo de aplicaciones móviles ha transitado desde enfoques imperativos hacia paradigmas declarativos y reactivos. Este cambio prioriza la eficiencia en el manejo de recursos limitados y asegura una interacción continua con el usuario.

\subsection{Arquitectura de Plataforma Android}

Su arquitectura se divide en capas: el kernel de Linux, la capa de abstracción de hardware (HAL), el tiempo de ejecución de Android (ART) y el marco de trabajo de aplicaciones (Application Framework) \cite{android_arch}.

El desarrollo nativo, utilizando el Android SDK (Software Development Kit), permite un acceso directo a las APIs del sistema. En consecuencia, este enfoque proporciona un rendimiento optimizado en comparación con soluciones híbridas, aspecto relevante en tareas intensivas como la inferencia de modelos de IA \cite{android_programming}.

La evolución de las interfaces de usuario en Android ha dado lugar a una transición desde la manipulación manual de vistas hacia un modelo basado en el estado. Este cambio busca reducir la complejidad en la sincronización de datos y mejorar la mantenibilidad del código visual. Cuando el estado cambia, el marco de trabajo ejecuta un proceso de Recomposición. Este proceso actualiza de forma selectiva los componentes que dependen de los datos modificados. De esta forma, se reduce la complejidad de sincronización manual entre la vista y el modelo \cite{gupta2022modern}.

\subsection{Ciclo de Vida y Gestión de Estado (UDF)}
La gestión de estado es crítica en aplicaciones reactivas para garantizar la consistencia de los datos mostrados. Se utiliza el patrón Unidirectional Data Flow (UDF), donde el estado fluye en una sola dirección (de la lógica a la UI) y los eventos fluyen en sentido contrario (de la UI a la lógica).

Para implementar este patrón, se emplean flujos reactivos mediante StateFlow de la librería Kotlin Coroutines. StateFlow es un flujo observable que emite actualizaciones de estado inmutables a la interfaz de usuario. Por lo tanto, se garantiza que la interfaz refleje el último estado válido producido por la capa de lógica de negocio \cite{reactive_kotlin}.

\subsection{Verificación y Rendimiento en Android}
La calidad de una aplicación móvil se evalúa mediante atributos funcionales y no funcionales. ISO/IEC 25010 organiza la calidad del producto de software en características como adecuación funcional, eficiencia de desempeño, compatibilidad, usabilidad, fiabilidad, seguridad, mantenibilidad y portabilidad \cite{iso25010-2011}. En aplicaciones Android, estas características se verifican combinando pruebas locales, instrumentadas, de interfaz, de rendimiento y de compatibilidad.

La documentación oficial de Android distingue las pruebas locales, ejecutadas en la máquina de desarrollo, de las pruebas instrumentadas, ejecutadas en un dispositivo físico o emulado \cite{android_testing_fundamentals}. Las primeras son adecuadas para validar clases, métodos y reglas de dominio con rapidez. Las segundas permiten comprobar integración con el sistema operativo, recursos Android, ciclo de vida de actividades e interacción de usuario.

En interfaces construidas con Jetpack Compose, las pruebas de interfaz utilizan nodos semánticos para localizar textos, descripciones de contenido, etiquetas y estados de componentes \cite{android_compose_testing}. Este enfoque permite validar la interfaz sin depender de coordenadas absolutas de pantalla. Para flujos que cruzan la aplicación completa o interactúan con elementos del sistema, UI Automator proporciona APIs de automatización que operan fuera del proceso de la aplicación \cite{android_uiautomator}.

Las pruebas de rendimiento en Android requieren mediciones repetibles sobre dispositivos reales o emulados. AndroidX Macrobenchmark permite medir inicio de aplicación, fluidez de cuadros y secciones de traza definidas por el desarrollador, generando reportes y trazas Perfetto para análisis posterior \cite{android_macrobenchmark}. Por ello, resulta adecuado para validar operaciones intensivas como la generación automatizada de horarios y la navegación principal.

\section{Arquitectura de Software}
\label{sec:arquitectura-software}

Para garantizar la mantenibilidad, facilidad de prueba y escalabilidad del software, se siguen principios de diseño robustos y patrones arquitectónicos estandarizados en la industria.

\subsection{Clean Architecture y Regla de Dependencia}
Clean Architecture, propuesta por Robert C. Martin \cite{martin2017-cleanarch}, constituye una filosofía de diseño orientada a la creación de sistemas con un elevado nivel de mantenibilidad. Este enfoque plantea una organización del software basada en la separación estricta de las reglas de negocio respecto a los detalles técnicos de infraestructura. Por lo tanto, se busca reducir el acoplamiento entre componentes y asegurar que el núcleo del sistema permanezca inalterado ante cambios en bases de datos o interfaces de usuario.

El pilar fundamental de este modelo es la Regla de Dependencia, la cual establece que las dependencias de código fuente solo deben apuntar hacia el centro de la arquitectura. Las capas internas no poseen conocimiento sobre los mecanismos de implementación situados en los niveles externos. Esta jerarquía garantiza que las reglas de negocio, representadas por entidades y casos de uso, sean los elementos de mayor estabilidad y protección dentro del sistema.

Como resultado de esta organización, el software adquiere independencia tecnológica y facilita los procesos de verificación de calidad. La lógica central se puede someter a pruebas de forma aislada sin requerir la presencia de servidores o elementos visuales. Esta capacidad de abstracción permite que la aplicación evolucione con agilidad, facilitando el reemplazo de herramientas o servicios de terceros con un impacto mínimo en el funcionamiento global.

La estructura de Clean Architecture se organiza en un conjunto de niveles concéntricos donde cada capa asume una responsabilidad específica, permitiendo un desacoplamiento efectivo entre la lógica central y los detalles técnicos del sistema. A continuación, se detallan las capas fundamentales que componen este modelo arquitectónico:
\begin{itemize}
    \item Capa de Dominio (Domain): Representa el núcleo del sistema y contiene la lógica de negocio más estable, encapsulada en Entidades y Casos de Uso. Al ser la capa más interna, se mantiene independiente por completo de librerías externas, frameworks y cualquier detalle de implementación de infraestructura.
    \item Capa de Datos (Data): Se encarga de la persistencia y recuperación de información mediante la implementación de las interfaces definidas en el dominio. Su función principal es orquestar el flujo de datos provenientes de diversas fuentes, como bases de datos locales, sistemas de archivos o servicios web remotos.
    \item Capa de Presentación (Presentation): Actúa como la interfaz de interacción con el usuario, encargándose de traducir el estado del sistema en elementos visuales comprensibles. Asimismo, captura los eventos generados por el usuario para comunicarlos a las capas internas sin comprometer la integridad de la lógica de negocio.
\end{itemize}

Clean Architecture presenta ventajas en términos de mantenibilidad y escalabilidad a largo plazo, aunque requiere una inversión inicial mayor en la estructuración del código. Este patrón facilita la evolución del software al aislar la lógica de negocio de los detalles de implementación, permitiendo modificar capas individuales sin afectar al resto del sistema.

En el contexto de aplicaciones móviles, esta separación resulta especialmente valiosa debido a los frecuentes cambios en frameworks y componentes de interfaz que caracterizan al ecosistema Android. Esta arquitectura se compone de tres capas principales, cada una con responsabilidades específicas:

\begin{itemize}
    \item Capa de UI (User Interface): Responsable de renderizar los datos en la pantalla y capturar las interacciones del usuario. En aplicaciones modernas de Android, utiliza Jetpack Compose para construir interfaces declarativas y reactivas. Los componentes clave de esta capa incluyen Composables (funciones que describen la UI como una función del estado), ViewModels (gestionan el estado de la UI y sobreviven a cambios de configuración) y UI State (representación inmutable del estado actual de la pantalla).
    \item Capa de Dominio: Opcional pero altamente recomendada en aplicaciones complejas. Su propósito es encapsular la lógica de negocio que puede ser reutilizada por múltiples ViewModels, evitando duplicación de código. Los casos de uso (Use Cases) son el componente principal de esta capa. Cada caso de uso representa una acción específica del usuario y orquesta la interacción entre múltiples repositorios si es necesario.
    \item Capa de Datos: Fuente única de verdad (Single Source of Truth) de la aplicación. Expone los datos a través de repositorios, que pueden combinar información de múltiples fuentes: bases de datos locales, APIs remotas, o archivos del sistema \cite{android_data_layer_guide}.
\end{itemize}

\subsection{Patrón Model-View-ViewModel (MVVM)}
El patrón de diseño Model-View-ViewModel (MVVM) facilita la separación de responsabilidades entre la interfaz de usuario y la lógica de presentación. Esta estructura permite que la vista permanezca independiente de la lógica de negocio, comunicándose con el modelo a través de un mediador que gestiona el estado de forma reactiva.

La implementación de esta arquitectura promueve el desacoplamiento, facilitando los procesos de prueba y la reutilización de componentes en entornos de desarrollo móvil. \begin{itemize}

\subsection{Inyección de Dependencias (Hilt)}
La Inyección de Dependencias (DI) es un patrón de diseño donde los objetos reciben sus dependencias desde fuera en lugar de crearlas ellos mismos, promoviendo la Inversión de Control (IoC) \cite{dependency_injection_principles}. Hilt es la solución estándar de Google para DI en Android basada en Dagger. Reduce el código repetitivo y gestiona el ciclo de vida de los componentes, facilitando la modularidad y permitiendo el intercambio de implementaciones.

\section{Fundamentos Algorítmicos y de Optimización}
\label{sec:algoritmia}

El problema de generación de horarios académicos es conocido de manera formal en la literatura como University Course Timetabling Problem (UCTP). Este problema se aborda mediante diversas teorías y algoritmos de optimización.

\subsection{Teoría de Grafos en la Planificación}
La Teoría de Grafos proporciona un marco matemático robusto para modelar conflictos en problemas de planificación. El problema de horarios se puede representar como un problema de coloración de grafos (Graph Coloring Problem - GCP) \cite{lewis2015guide}.

En este modelo se tienen los siguientes elementos:
\begin{itemize}
    \item Vértices (Nodos): Representan los eventos o clases a programar.
    \item Aristas (Enlaces): Conectan dos vértices si existe un conflicto entre ellos (por ejemplo, mismo profesor, mismo grupo de estudiantes o misma aula).
    \item Colores: Representan los periodos de tiempo disponibles.
\end{itemize}

El objetivo es asignar un color a cada vértice de tal manera que ningunos dos vértices adyacentes compartan el mismo color, utilizando el mínimo número de colores posible (número cromático).

Algoritmos clásicos como Welsh-Powell o DSATUR (Degree of Saturation) son eficientes para encontrar soluciones en grafos de conflictos \cite{burke2004-state}. No obstante, las restricciones inherentes a la planificación académica (preferencias de docentes, minimización de huecos, restricciones de capacidad) limitan la aplicabilidad directa del modelo de coloración pura.

Por esta razón, aunque la teoría de grafos fundamenta el entendimiento de los conflictos, un enfoque alternativo y flexible es el uso de CSP y Backtracking.

\subsection{Problema de Satisfacción de Restricciones (CSP)}
El UCTP se modela matemáticamente como un Problema de Satisfacción de Restricciones (CSP), definido por Russell y Norvig \cite{russell2021ai} como una terna $(X, D, C)$:
\begin{itemize}
    \item $X$: Un conjunto de variables (las asignaturas a inscribir).
    \item $D$: Un conjunto de dominios (los grupos disponibles para cada asignatura).
    \item $C$: Un conjunto de restricciones que especifican combinaciones permitidas de valores.
\end{itemize}

Las restricciones se clasifican en Duras (Hard), que deben cumplirse de forma obligatoria (por ejemplo, no solapamiento de horarios), y Blandas (Soft), que expresan preferencias deseables pero no obligatorias (por ejemplo, minimizar huecos libres).

\subsection{Algoritmos de Búsqueda y Backtracking}
Para resolver problemas de tipo CSP, con frecuencia se utiliza el algoritmo de Backtracking (Vuelta Atrás). Este método realiza una búsqueda sistemática en el espacio de soluciones, explorando las posibles asignaciones de forma incremental y descartando ramas que violan las restricciones establecidas:

\begin{enumerate}
    \item Generación de Candidatos: El algoritmo construye soluciones de forma incremental, asignatura por asignatura.
    \item Verificación de Restricciones: En cada paso, verifica si la asignación actual viola alguna restricción dura.
    \item Retroceso (Backtrack): Si se encuentra un conflicto insalvable, el algoritmo retrocede al paso anterior y prueba con el siguiente grupo disponible, descartando la rama actual del árbol de búsqueda \cite{cormen_algorithms}.
\end{enumerate}

Este enfoque permite identificar combinaciones válidas de forma sistemática dentro del conjunto de candidatos explorado. Dicha característica resulta útil cuando se requiere presentar varias alternativas y no solo la primera solución factible.

La selección de un algoritmo para generación de horarios depende del tamaño del dominio, el tipo de restricciones y los recursos disponibles para la ejecución. En el caso de aplicaciones móviles, se requiere un equilibrio entre completitud, consumo de memoria y facilidad para incorporar preferencias del usuario. \subsection{Optimización Combinatoria y Selección}
Dado que el número de combinaciones válidas puede ser muy grande, se aplica un proceso de Optimización Combinatoria para seleccionar las mejores opciones. Los algoritmos de optimización no solo buscan una solución factible, sino que buscan las ``mejores $k$'' soluciones según criterios de calidad.

Se suele utilizar un sistema de ranking donde cada horario generado recibe una puntuación basada en el cumplimiento de restricciones blandas. Posteriormente, se ordenan las soluciones de mayor a menor puntaje y se presentan al usuario las opciones destacadas, facilitando el proceso de selección.

\subsection{Análisis de Decisión Multi-Criterio (MCDA)}
Para evaluar la calidad de un horario, se emplea el Análisis de Decisión Multi-criterio (MCDA). Este enfoque permite considerar múltiples factores al mismo tiempo, asignando pesos específicos a cada criterio \cite{triantaphyllou2000multi}.

En la práctica, esto se puede implementar a través del Patrón de Diseño \textit{Strategy}. Este patrón permite cambiar de forma dinámica la estrategia de evaluación (por ejemplo, ``Priorizar mañanas libres'', ``Minimizar huecos'', ``Evitar cruces de materias''), calculando el puntaje total como una suma ponderada de estos criterios. Esto otorga flexibilidad para adaptarse a las preferencias cambiantes.

\section{Inteligencia Artificial en Dispositivos Móviles (Edge AI)}
\label{sec:edge-ai}

La Inteligencia Artificial en el Borde (Edge AI) permite integrar capacidades de inteligencia artificial generativa ejecutándose directamente en el dispositivo móvil. Este paradigma elimina la dependencia de servidores externos, garantizando la privacidad de los datos del usuario y reduciendo la latencia de respuesta. Además, posibilita el funcionamiento de características inteligentes en escenarios sin conectividad a internet.

\subsection{Inferencia Local vs. Inferencia en la Nube}
La transición hacia el procesamiento local representa un cambio de paradigma en la implementación de servicios inteligentes, priorizando la ejecución en el hardware del cliente. A diferencia de las soluciones basadas en la nube, la Edge AI realiza el cómputo de datos de forma íntegra en el terminal.

Este enfoque minimiza los riesgos asociados a la transferencia de información sensible. Asimismo, asegura una operatividad constante bajo diversas condiciones de red.

La adopción de este modelo responde a la necesidad de reducir los tiempos de respuesta en aplicaciones críticas. Se evitan los retardos inherentes a la comunicación con servidores remotos.

Asimismo, el uso de recursos locales disminuye los costos operativos de infraestructura. Esto permite el aprovechamiento de procesadores especializados en inteligencia artificial en los dispositivos modernos. \subsection{Modelos de Lenguaje (LLMs) y Cuantización}
Para viabilizar la ejecución de Large Language Models (LLMs) en dispositivos con recursos limitados, se utiliza la técnica de Cuantización. Este proceso reduce la precisión de los pesos del modelo (de punto flotante de 16 bits a enteros de 4 bits), disminuyendo el tamaño y consumo de memoria con pérdida mínima de precisión \cite{quantization_papers}. El formato GGUF está optimizado para inferencia rápida en CPU.

\subsection{Parámetros de Muestreo en Generación de Texto}
La generación de texto en LLMs utiliza diversos parámetros de muestreo (sampling) que controlan la aleatoriedad y calidad de las respuestas:

\begin{itemize}
    \item Temperature: Controla la aleatoriedad. Valores bajos (0.1-0.5) producen respuestas más determinísticas, mientras valores altos (0.8-1.5) generan mayor variedad.
    \item Top-P (Nucleus Sampling): Limita la selección a tokens cuya probabilidad acumulada no exceda el umbral P.
    \item Top-K: Restringe la selección a los K tokens más probables.
    \item Repeat Penalty: Penaliza la repetición de tokens para evitar bucles en la generación.
\end{itemize}

La combinación adecuada de estos parámetros permite optimizar la generación según el caso de uso específico \cite{holtzman2020curious}.

\section{Adquisición y Procesamiento de Datos}

La integración de información proveniente de fuentes externas heterogéneas constituye un desafío técnico significativo debido a la ausencia de formatos estandarizados. Con frecuencia, los datos requeridos se encuentran alojados en portales web sin una API estructurada o en documentos de formato fijo como archivos PDF.

El procesamiento de estos recursos exige la implementación de técnicas de extracción especializadas. Estos métodos permiten transformar contenido no estructurado en esquemas de datos procesables por la lógica de negocio.

Para abordar esta problemática, se emplean métodos de recolección automatizada conocidos como web scraping. Estas herramientas permiten navegar y capturar información relevante directamente desde la capa visual de los sitios web.

Asimismo, el análisis de documentos digitales requiere motores de extracción capaces de interpretar la jerarquía de textos y tablas en estructuras complejas. Estos procesos aseguran la interoperabilidad con sistemas externos y la actualización constante de la base de conocimientos.

\section{Notificaciones y Widgets en Android}
\label{sec:notificaciones-widgets}

Android proporciona mecanismos para interactuar con el usuario cuando la aplicación no está en primer plano: Notificaciones y App Widgets.

\subsection{Sistema de Notificaciones}
Las notificaciones son mensajes mostrados fuera de la interfaz de la aplicación \cite{android_notifications}. A partir de Android 8.0, deben asignarse a un Canal de Notificación (Notification Channel), permitiendo agruparlas por tipo y configurar sonido, vibración e importancia \cite{android_notification_channels}.

Existen dos tipos principales: Notificaciones Locales, programadas con WorkManager para recordatorios basados en tiempo, y Notificaciones Remotas (Push), enviadas desde servidores externos mediante Firebase Cloud Messaging (FCM).

\subsection{App Widgets}
Los App Widgets son vistas miniatura incrustables en la pantalla de inicio \cite{android_widgets}. Su arquitectura se basa en AppWidgetProvider (BroadcastReceiver que maneja el ciclo de vida) y RemoteViews (describe vistas ejecutables en otro proceso) \cite{android_remoteviews}.
